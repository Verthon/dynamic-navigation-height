# Sidebar offset across a micro-frontend boundary

## System as is

```
app ── renders ──> core <CoreProvider>
                     └─ core <Layout navigation sidebar footer>   (optional: apps may compose their own)
                          ├─ NavigationWrapper | ExtendedNavigationWrapper ──loads──> Navigation MF | ExtendedNavigation MF
                          ├─ SidebarWrapper ─────────────────────────────────loads──> Sidebar MF
                          └─ FooterWrapper ──────────────────────────────────loads──> Footer MF
each MF ── bundles its own copy of core (not shared) + uses the DS
```

- **app** (`src/App.tsx`): picks the navigation, sidebar and footer per route and passes them to `<Layout>` with its
  page content. Wrappers take no props: the app never passes heights or other dimensions.
  - Not every team uses `Layout`; some compose the same wrappers in their own layout.
- **core** (`src/core/`): `Layout`, `CoreProvider`, wrappers, skeletons, private height table
  (`default` 64px, `extended` 112px).
  - `Layout` only places the slots; it doesn't know the nav variant.
  - `CoreProvider` imports core's base CSS; it doesn't know the nav variant either.
- **skeletons** (core): shown while a MF loads.
  - navigation skeletons: `header`, `sticky`, `top: 0`, height from core's table → correct.
  - sidebar skeleton: `top: 64` **hardcoded** (today's core, `hardcoded` scenario).
- **DS** (stand-in: `src/micro-frontends/ds.ts`): `DESKTOP_NAVIGATION_HEIGHT = 64`; the DS applies it as the
  navigation's min-height.
- **Navigation MFs**: 64px row (DS min-height); extended adds a 48px sub-nav → 112px.
- **Sidebar MF**: its own code uses `DESKTOP_NAVIGATION_HEIGHT` for `top: 64` and
  `height: calc(100vh / zoom - 64px)`; width 264.
- **Footer MF**: zoom buttons, set `--core-body-zoom` on `<body>`.
- **core copy** (`src/micro-frontends/core-copy/`): generated by `npm run sync-core`; a separate bundled copy, not
  shared with the app's core.

### Key CSS

| Element | File | `position` | `top` | Height |
| --- | --- | --- | --- | --- |
| nav skeleton (`<header>`) | `src/core/skeletons.tsx` | `sticky` | `0` | 64 / 112 from core's table |
| nav MF (`<header>`) | `src/micro-frontends/header-parts.tsx` | `sticky` | `0` | min-height 64 (DS) + 48 sub-nav |
| sidebar skeleton (`<aside>`) | `src/core/skeletons.tsx`, `top` passed in `src/core/wrappers.tsx` | `sticky` | **`64` hardcoded** | `calc(100vh / zoom - 64px)` |
| sidebar MF (`<aside>`) | `src/micro-frontends/Sidebar.tsx` | `sticky` | **`64` hardcoded** (`DESKTOP_NAVIGATION_HEIGHT`) | `calc(100vh / zoom - 64px)` |

- Headers: `z-index: 10`, so content scrolls under them.
- Sidebar + `<main>` sit in one `display: flex` row (`src/core/Layout.tsx`, or the team's own layout); the sidebar
  sticks inside it.
- `zoom` = `var(--core-body-zoom, 1)`: set on `<body>` only by the Footer MF (core never sets it); unset → `1`.

## Problem

- Every desktop nav used to be 64px, so hardcoding 64 was fine.
- The extended nav is 112px. Skeleton and sidebar still assume 64px:
  - top 48px of the sidebar hides under the header;
  - sidebar is 48px too tall.
- See it: `/s/hardcoded?nav=extended`.
- A fix must cover both the core skeleton and the Sidebar MF. If only one is fixed, they disagree (64 vs 112) and the
  page jumps when the MF replaces the skeleton.
- Constraints on where the height comes from:
  - `Layout` gets the navigation as a component, not a variant, so it can't look the height up.
  - Some teams don't use `Layout` at all, so the fix can't depend on it (or on `CoreProvider`).
  - It must be in the SSR HTML; measuring the header in JS comes too late and the page jumps.

## Solution 1 (recommended): CSS variable `--core-header-height`

1. The app renders one of core's nav wrappers (`NavigationWrapper` / `ExtendedNavigationWrapper`), with or without
   `Layout`.
2. The wrapper renders `<HeaderHeight>` (`src/core/HeaderHeight.tsx`): a plain
   `<style nonce>:root{--core-header-height:112px}</style>`, height from core's private table.
3. It sits outside `Suspense`, so it's in the first SSR chunk, before any skeleton.
4. The variable is on `:root`, so every element inherits it, across the MF boundary and in any layout.
5. Core's sidebar skeleton and the Sidebar MF read `var(--core-header-height, 64px)`.

- Only the wrapper knows the variant; `Layout`, `CoreProvider` and the Sidebar MF don't.
- The `<style>` is removed when the wrapper unmounts, so routes with different navs just work.
- MFs also bundle core, but never render the nav wrappers. Only the core version **installed in the app** decides
  whether the variable is set.

### Core repo

- [x] Nav wrappers render `<HeaderHeight variant>` outside `Suspense`.
  - Plain `<style>`, no styled-components; no CSS file, so `sideEffects: false` can't tree-shake it away.
  - Nonce: from the per-request global on the server, from the page's `<script nonce>` in the browser.
    `suppressHydrationWarning`, because browsers hide `nonce` from the DOM under a CSP header.
- [x] `CoreProvider` no longer takes `nav` or sets the variable.
- [x] `SidebarSkeleton`: `top` / `height` from `var(--core-header-height, 64px)` instead of `64`.

### Micro-frontends repo (Sidebar)

- [x] `top` / `height` from `var(--core-header-height, 64px)`; fallback = `DESKTOP_NAVIGATION_HEIGHT`.
- No core bump needed:
  - it reads a CSS string, not core code;
  - bumping its core copy changes nothing here;
  - the variable comes only from the core installed in the app.

### Rollout

1. Sidebar MF first: old cores don't set the variable → fallback 64 = today.
2. Then apps upgrade core when they like.

- Wrong order (core first): skeleton 112, old sidebar 64 → page jumps on swap.

### Trade-offs

- The variable name is an unchecked contract: a typo silently falls back to 64.
- Heights live in two places: core's table and the nav MFs.
  - A nav height change needs a core release + app rebuilds.
- Works only through core's nav wrappers: a team that loads a nav MF directly gets the 64px fallback.
- Two navs on one page would both set the variable; the last `<style>` wins.
- The `<style>` sits in `<body>`: invalid HTML strictly speaking, but every browser applies it.

### Repro

- `/s/cssvar?nav=extended`: new core + new MF; skeleton and sidebar both at 112.
- `/s/legacy?nav=extended`: new MF, old core (no variable) → both at 64, same as today.

## Rejected: core passes the height as a prop

Idea: core's `SidebarWrapper` passes `headerHeight={112}` to the Sidebar MF, and the MF uses it for `top` / `height`.

- Consumers render wrappers with **zero props** (`<ExtendedNavigationWrapper />`, `<SidebarWrapper />`). The app
  must never pass dimensions: they're core's / the MFs' business, and core's height table stays private.
- With zero props, `SidebarWrapper` has no way to know the height:
  - the nav and the sidebar are **siblings** (two separate `Layout` slots, or two separate elements in a custom
    layout); React context only flows down, never sibling to sibling;
  - `Layout` gets the navigation as an element, not a variant, and some teams don't use `Layout` at all.
- Making it work needs a hidden channel between the two wrappers (e.g. the nav wrapper writes its variant into a
  store during render, the sidebar wrapper reads it later in the same render). That relies on render order and on
  side effects during render. Too fragile.
- The old-core problem: a new Sidebar MF that expects the prop gets nothing from an app on an older core, so the MF
  needs a fallback anyway. That's the same 64px fallback the CSS variable gives for free.
- The CSS variable already gets from nav to sidebar across the tree (it's on `:root`), with no wrapper coordination
  and no props. → Solution 1.

An earlier version of the repro ran this as a `props` scenario. To do that, the app computed the height and passed
`headerHeight` to `SidebarWrapper`, which is the leak described above. The scenario has been removed.

## Repro mechanics

- Fake Module Federation (`src/core/remotes.ts`): `remoteEntry.js` ~200ms, then chunk (nav ~0.6s, sidebar ~1s,
  footer ~1.4s). No caching, so every load shows skeletons.
- Streaming SSR: shell + skeletons first, each MF streamed in as it arrives. Logs: `[mf:server]` / `[mf:client]`.
- Scenarios (`src/core/scenarios.tsx`, repro-only): each one = which **core version** the app has installed + which
  **Sidebar MF build** is deployed.

  | Scenario | Core | Sidebar MF |
  | --- | --- | --- |
  | `hardcoded` | today (skeleton 64, no variable) | hardcoded 64 |
  | `cssvar` | new (sets the variable, skeleton reads it) | reads the variable |
  | `legacy` | today | reads the variable |

  - In production there's one of each, so consumers never choose. In the repro, `ScenarioPage` (`src/App.tsx`)
    reads the URL and wraps the page in `<ScenarioProvider>`; core's wrappers read it with `useScenario()`.
  - The consumer JSX (`Page` in `src/App.tsx`) has no repro props, so it reads like real usage.
  - `SidebarWrapper` passes `version` to the Sidebar MF to pick the deployed build (the MF has its own core copy,
    so it can't read core's context). Repro-only. A real MF has no such prop.
